> 本文剖析 GPU 计算中心化 2D 渲染器 Vello 的底层算法：为什么它不做三角化，它如何把"本质串行"的 2D 渲染变成大规模并行计算，以及支撑整个架构的两根技术支柱——sort-middle 管线与 prefix-sum 并行化。

## 一、引言：一个反直觉的选择

传统 GPU 矢量渲染（如 Skia 的 GPU path rendering）的标准做法是**三角化（tessellation）**：把贝塞尔曲线切成大量三角形，交给 GPU 的三角形光栅固定管线去画，抗锯齿靠 MSAA 采样。

Vello 反其道而行：**它完全不经过三角形管线**。所有工作跑在计算着色器（compute shader）里，曲线被细分为线段，每个像素的覆盖值（coverage）由**解析面积积分**精确算出。在 M1 Max 上，它渲染 paris-30k（3 万条路径的巴黎街景图）测试场景可达 177 fps。

要理解这套架构如何可能，需要两根支柱：

1. **Sort-middle 管线**：把整个渲染器重组为"排序发生在中段"的流水线，使乱序并行与顺序正确性共存；
2. **Prefix-sum 并行化**：把渲染中一切"顺序依赖"改写成 GPU 上最快的并行原语——前缀和扫描。

这两根支柱不是并列的两个特性，而是"一套思想的两层"：sort-middle 是组织方式，prefix-sum 是让每一站都能并行起来的发动机。

## 二、算法总览：三步走，不画三角形

Vello 对矢量图形的处理分三个阶段：

<img src="/assets/img/vello-pipeline.svg" alt="Vello 渲染三步走：曲线线段化、tile 分箱与绕数记账、逐像素解析面积积分" style="display:block; width:451px; max-width:100%; height:auto; margin:1em auto;">

**第①步：线段化而非三角化。** 三次/二次贝塞尔、椭圆弧在 GPU 上按曲率自适应细分成线段，每条曲线独立处理、完全并行。因为细分在 GPU 上按当前变换进行，放大视图时自动切得更密。描边（stroke）在同一阶段解决：不是画平行线，而是把中心线转换成等距轮廓曲线（stroke expansion）。难点在于数学上"平行曲线一般不是贝塞尔曲线"——Vello 用 Euler spiral（欧拉螺线）拟合解决这个问题，这也是 Raph Levien 的标志性工作之一。

**第②③步：解析覆盖而非采样。** 传统 MSAA 是采样：每像素打若干子采样点，数命中数。Vello 的 fine shader 对每个像素做解析积分：对穿过像素的每条线段计算其与像素方框相交的有符号梯形面积，沿扫描方向累加得到绕数（winding number），再按填充规则转成 0~1 的 alpha。没有超采样、没有近似——边缘质量与缩放级别无关，放大 100 倍也不失真。

三角化路线的痛点是**几何放大**：一个平滑圆角矩形产生成百上千个三角形，曲线越精细顶点越多；而 Vello 的线段是细粒度数据，由高度并行的 compute 逐 tile 消费，管线吞吐与场景元素总数成正比——作者称之为 **"performance smoothness"**（性能平滑、无悬崖）：海量简单路径与少量复杂路径的渲染成本接近。

至此留下的核心问题是：这三步在 GPU 上如何组织？顺序敏感的环节（图形状态、填充内部、输出分配）如何并行化？答案就是下面两根支柱。

## 三、支柱一：Sort-middle 管线

### 3.1 名字的出处

"Sort-middle" 借自 2011 年 Laine 和 Karras 的论文 *High-Performance Software Rasterization on GPUs*（及其实现 cudaraster）：在纯计算着色器管线的**中段**插入一次排序，使前段可以任意顺序乱序处理元素以榨干并行度，后段拿到的元素却恢复正确顺序，从而保证顺序敏感操作的正确性。在 3D 里你"差不多"可以不用排序（靠 Z-buffer），但那会产生 Z-fighting 和半透明问题；在 2D 里绘制顺序（painter's algorithm）是语义的一部分，排序不可省略。

### 3.2 第一步改造：把场景变成"元素流"

早期 piet-metal/piet-gpu 把场景存成一棵树，每个负责一块屏幕区域的 workgroup 各自从头遍历——同一批节点被反复读取，节点子元素太多或太少时性能都塌方。新架构的关键决策：**场景是一串定长元素的有序序列**（"拼接仿射变换""设置线宽""填充用线段""fill""stroke"……）。红利是每个元素在流水线前段只被碰一次，图层（layer）可以直接退化成字节的拼接。代价是放弃 `save`/`restore` 压栈（状态必须固定大小），改用 CPU 端编码逆变换模拟 restore。

### 3.3 管线的四个阶段

**① 元素处理（scan）**：每个元素标注三样状态——线宽、当前仿射变换、包围盒。这些状态天然是"当前值依赖前面所有元素"的串行计算，解法见支柱二（prefix-sum）。此阶段极快，几乎不贡献渲染耗时。

**② 分箱（binning）**：渲染目标切成 256×256 像素的 bin，按包围盒把元素分派到它触及的所有 bin。与 cudaraster 的链表方案不同，每个 bin × 分区输出一段连续区间，段内保持有序——牺牲一点空段，换来下一步的高并行连续读。各 workgroup 之间无需同步。

**③ 粗光栅化（coarse rasterization）**：全管线最重的一段，内部又分四个子阶段：

- **合并**：反复读取分箱段，把 256 个元素恢复全局有序——"sort"就发生在这里；
- **输入**：每线程读一个元素，把它对 16×16 tile 阵列的覆盖算成位图（fat line rasterization）；
- **分配**：统计线段总数，用前缀和/原子加申请输出空间，再均摊到各线程；
- **输出**：每 tile 一个线程顺序写出该 tile 的命令列表（命令数远少于线段数，这个尺度上串行反而是最优的）。

**④ 细光栅化（fine rasterization）**：每个 tile 拿到自己的命令，做第二节描述的解析面积积分，blend 后写出。此时顺序问题已全部解决，是完全"尴尬并行"的。

### 3.4 填充实心内部的 trick：backdrop

"填充区域内部"是个非局部问题：一个远在 800 像素外的边可能决定当前 tile 是否在图形内部。Vello 把它拆成三条纯局部规则，组合后绕数自动正确：

1. tile 内，线段使其**右侧**区域绕数 ±1（方向反转变号）；
2. 线段若**跨越竖直 tile 边界**，给下方半格额外 −1；
3. 线段若**跨越水平 tile 边界**（tile 顶边），给右侧所有 tile +1——即 **backdrop 传播**，让深处无边的 tile 也能被填上。

工程上麻烦的是 backdrop 需要从扫描阶段起就把 fill 的右边界往回传播给每条线段，记账横跨三个阶段。这套思想在 RAVG 论文中有另一个表述。

### 3.5 这套架构买到什么

**性能平滑（performance smoothness）**：成本大致正比于场景元素总数。"海量简单路径"（散点图）与"少量极复杂路径"（paris-30k）性能接近，变换数量多也不在乎。对比之下，旧架构只在"节点子元素数量适中"时高效。

代价也有：排序只发生在必要处是这套架构的精髓，但"让线段全局有序"本身有开销；且 GPU 间性能特征差异大——同一实现在 GTX 1060 上 paris-30k 提速明显，在 Intel 核显上收益缩水甚至回退（作者怀疑与共享内存较慢有关）。Raph Levien 后来意识到：路径内部的线段其实无需全局有序，只需归属到正确的"路径 × tile"二元组——这为后续演进留下了伏笔。

## 四、支柱二：Prefix-sum 并行化

### 4.1 为什么前缀和是核心原语

前缀和（scan）定义朴素：给定序列与可结合的 combine 操作，输出每个位置之前的累积。但它几乎是所有"顺序依赖"的通用解法：流压缩、变长数据解码、**输出空间分配**、以及最关键的——**在 GPU 上模拟状态机**。Raph Levien 后来说得很直白：他最初写前缀和的博文时只觉得"可能对 2D 有用"，没想到它会成为整个架构的中心；元素处理阶段只做了一点小改动就复用了那套实现，而且快得惊人。

### 4.2 "几乎 monoid"：把图形状态变成可结合的操作

scan 成立的前提是 combine 操作满足结合律（不必交换）。Vello 的状态恰好"差不多"满足：

- **变换**：仿射矩阵连乘，天然结合（不交换）；
- **线宽**：后写覆盖先写——经典的"last-wins"结合操作；
- **包围盒**：并集结合且交换，加几个 flag 处理 fill/stroke 处的重置语义。

唯一的妥协：仿射变换与轴对齐包围盒**不严格分配**（先变换再求并 ≠ 先求并再变换，结果偏大）。但包围盒只用于分箱，允许保守，所以"almost monoid"就够。这个抽象的漂亮之处在于：**一段元素切片对状态的效果，与切片内部如何划分无关**——这正是并行 scan 能把它切成任意小块、分头算再合并的理论基础。

### 4.3 单趟实现：decoupled look-back 与"memcpy 速度"

教科书式 GPU scan 是树形归约 + 重扫：多次 dispatch，输入读两遍，吞吐上限只有 memcpy 的约 2/3。Vello 用的是 Merrill 和 Garland 2016 年提出的 **decoupled look-back（解耦回溯）**：每个 workgroup 先发布本块的归约值，然后边等左边邻居的前缀值边向更左回溯求和，一旦拿到就直接产出自己的前缀——全管线**单趟**完成，在 AMD 5700 XT 上跑到约 46–48 G 元素/秒，基本等于 memcpy 带宽。

### 4.4 可移植性之殇：单趟 scan 的硬件门槛

单趟 scan 有个隐藏依赖：workgroup 之间需要"消息传递"式协调（写数据→设标志位→对方读到标志再读数据），这要求 device 级 barrier / 原子内存序和 **forward-progress 保证**。实测结果：

- Vulkan、CUDA、DX12 都支持；
- **Metal 不行**，因此 WebGPU 也不行（以 Metal 为最差公分母）——Metal 上至少要拆成两次 dispatch，吞吐受损，还要按问题尺寸写一堆 shader 变体；Vello 一度因此处理不了超过 64k 条路径段。更坑的是 MoltenVK 会把正确的 SPIR-V **静默翻译成缺 barrier 的 MSL**——"最漏的抽象层"。

这段历史直接影响了 Vello 的工程决策：正因为自研硬件抽象层要填这么多坑（还包括用前缀和压力测试抓到的 5700 XT 原子内存序真实硬件 bug），Raph Levien 才写下《Requiem for piet-gpu-hal》，放弃自定义 HAL、全面转向 wgpu——牺牲一点峰值性能，换可移植性与正确性。

值得品味的对称性：**排序只发生在必要的地方**——路径内部线段其实无需全局有序，只需归属正确的"路径 × tile"二元组；backdrop 把"非局部填充"改写成向右一维传播的局部规则；一切本该串行的地方，要么被改写成 scan，要么被推迟到"每 tile 一个线程"的串行小循环里——那个尺度上串行是最优的。

把前面所有章节收拢成一条公式化的理解：**prefix-sum 让"状态"可并行，sort-middle 让"顺序"有边界，解析覆盖让"质量"无近似**——三者相乘，得到一个无性能悬崖、无缩放失真、跨平台行为一致的渲染器。

## 六、字形与描边：同一个数学问题

字形没有特殊通道：parley/skrifa 给出 glyph 轮廓（就是 path），丢进完全相同的"flatten → 分箱 → 解析覆盖"管线。矢量图形与文字在 Vello 里是同一个数学问题的两种输入。

描边的 stroke expansion（Euler spiral 拟合等距轮廓）值得一提：它让"描边"在数学上归约为"填充"，从而免费获得与填充一致的抗锯齿质量和填充规则语义。

## 七、后续演进：当 compute 不是随处可得

纯 compute 管线虽优雅，但依赖 compute shader：移动端/浏览器支持参差，且 GPU 内存占用存在悬崖。2024 年后的新方向 **Sparse Strips**（vello_cpu / vello_hybrid）基于 Raph Levien 的《Potato: a hybrid CPU/GPU 2D renderer design》：只用 fragment/vertex shader 也能跑，并配套多线程 SIMD 的 CPU 渲染器（4×4 tile 配 f32x4，只存储有边缘区域的覆盖值）。关键在"解析覆盖"的基因被完整保留——今天 Vello 已从一个引擎变成一族共享同一成像模型的渲染器，而 sort-middle 与 prefix-sum 的思想仍在每一个实现里流淌。
